This statement covers this website, the GGDS documentation, and the GGDS styles, script and page parts it shows. It was prepared on 10 November 2026, for version ${version}.

Every government website that uses GGDS needs its own accessibility statement: GGDS makes its parts accessible, but each website's own content, pages and services need checking too. You can start from the structure of this one.

How accessible GGDS is

GGDS aims to meet the Web Content Accessibility Guidelines (WCAG) 2.2 at level AA. We think it meets level AA in what automated tests can check. It has not yet been tested by an accessibility auditor or by disabled people, so we do not yet claim that it fully meets level AA.

You should be able to:

  • use every page with a keyboard only, and always see where you are, with a gold focus outline;
  • use a screen reader: every page has a skip link, headings in order, labelled landmarks and labelled form fields;
  • use a phone as narrow as 320 pixels without scrolling sideways;
  • zoom in, change the text size, and use Windows contrast themes;
  • use every page and every form without JavaScript;
  • read every text and see every border and focus outline: each colour pair meets its contrast minimum.

Animations play only if you have not asked your device for less motion, and everything that moves on its own stops within 5 seconds.

How we test

On every change, before it can be released:

  • Automated accessibility checks (axe, WCAG 2.2 A and AA rules) on every page of this website, including every live example, in Chrome at desktop and phone widths.
  • Sideways scrolling at 320 pixels, also with a wide font, on every live example and the main documentation pages.
  • Contrast of every colour pair GGDS uses, for the default and every institution theme.
  • Behaviour tests: the phone menu opens in place, Escape closes it and focus returns to its button; the error summary takes focus and its links reach each field; the banner opens; pagination keeps the search.
  • Movement: the moving drawings stop within 5 seconds of loading, so they need no pause button (WCAG 2.2.2).
  • Content Security Policy: every page runs with no inline scripts or styles.

Automated tests find only some of the barriers people meet. Each component page lists its tests, including the checks by people that are still to do: keyboard only, NVDA, JAWS, VoiceOver, TalkBack, zoom to 400%, Windows contrast themes and voice control.

What is not accessible or not tested yet

  • No audit yet. An external accessibility auditor, working with Ghanaian disability organisations, will test GGDS before version 1.0 (decision D-09). Until then, results by people are not recorded on the component pages.
  • Screen readers and voice control have not been tested with each component.
  • Languages. GGDS's text and examples are in English only. Pages in Ghanaian languages need their own lang attribute and testing with speakers of those languages.
  • Live examples in frames. Component pages show each example in a frame with a title. Each example also opens as its own page, which is easier to use with some screen readers and magnifiers.

Tell us about a problem

If you find a problem with GGDS or this website, or you cannot use something, please tell us. We want to hear from disabled people especially.

  • Report an accessibility problem on GitHub (you need a GitHub account).
  • Say which page or component, what you were trying to do, and what you use, such as a screen reader, magnifier or voice control, if you are happy to.

We aim to reply within 5 working days. GGDS is maintained by the National Information Technology Agency (NITA). A contact for people without a GitHub account will be added here once NITA confirms one.

For websites using GGDS

Using GGDS does not make a website accessible on its own. You still need to:

  • write clear content, with headings in order and link text that makes sense on its own (see Get started as a content designer);
  • follow the "What you need to do" part of each component's guidance;
  • test your own pages and services, including with disabled people, before launch;
  • publish your own accessibility statement and answer the problems people report.
